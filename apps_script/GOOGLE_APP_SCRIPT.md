# Wiring the Review Workflow to Google Sheets

This file describes the human review interface shared by **both** review tabs of the
spreadsheet:

- **`Agent_suggestions`** — non-deterministic AI suggestions (uploaded manually after an enrichment run via `journal-metadata-enrichment/agent/scripts/upload_suggestions.py`)
- **`Disagreements`** — deterministic conflicts between the dataset and external sources (Scimago, OpenAPC, DOAJ) plus internal Publisher-type checks, regenerated on every pipeline run and uploaded by `scripts/upload_sheets.py`; when more than 10 higher-priority rows exist, 'Low' priority rows are left out of the upload — the full report stays in the CSV)

Both tabs are generated by the same shared code (`scripts/review_common.py` of this
repository), share the same row schema, and are processed by a single Google Apps
Script.

## 1. Shared Review-Row Schema

Every review tab starts with these columns:

| Column            | Meaning                                                        |
| ----------------- | -------------------------------------------------------------- |
| `Status`          | dropdown: `pending` / `approve` / `reject` (new rows: `pending`) |
| `journal`         | journal the row targets (Table shows context)                  |
| `field`           | data-tab column to change (e.g. `Business model`, `e-ISSN`)    |
| `current_value`   | dataset value recorded when the row was generated (verification) |
| `suggested_value` | value written into the data tab on approval                    |
| `suggestion_type` | `fill` / `correct` / `alt_name` / `remove`                     |
| `data_tab`        | data tab holding the target cell (e.g. `Cancer`)               |
| `target_row`      | 1-based row number of the target cell                          |
| `target_col`      | 1-based column number of the target cell                       |

Tab-specific middle columns (`Disagreements`: url, reasoning,
Scimago/DOAJ/OpenAPC values; `Agent_suggestions`: confidence, source_urls,
reasoning).
The `reasoning` column of both tabs is a factual justification of the row —
for disagreements it states which sources report which value, whether they
agree or contradict each other, and (for Publisher rows) the publisher type
each source implies — so the reviewer can judge the row from facts.

The target cell is recorded at upload time so the Apps Script never scans the
data tabs — it verifies the cell (see below) and performs a single-cell write.
If a recorded target cannot be resolved (journal unknown or found in multiple
tabs), the target columns are empty and the row must be handled manually.

## 2. Install the Apps Script

1. Open the spreadsheet.
2. Extensions → Apps Script.
3. Paste the content of [`apps_script/ApplyReviewedChanges.gs`](apps_script/ApplyReviewedChanges.gs) and save.
4. Run → Run function → `onOpen` (to register the menu).
5. Return to the spreadsheet. You should see the "WhereToPublish" menu with:
   - **Review Disagreements** — opens the `Disagreements` tab
   - **Review Agent suggestions** — opens the `Agent_suggestions` tab
   - **Apply Reviewed Changes** — processes the approve/reject rows of both tabs

The script supports both review tabs listed in its `REVIEW_TABS` constant and
keeps the backwards-compatible `applyReviewedSuggestions` alias for menus created
with the previous version.

### How approvals are applied (fast and verified)

For each `approve` row the script:

1. looks up the data tab from `data_tab` (header row read once per tab per run — no full-tab scans),
2. verifies the column header at `target_col` still equals `field`,
3. verifies the Journal cell of `target_row` still equals `journal` (detects moved/inserted rows),
4. verifies the target cell still holds `current_value` (detects any change since the report was generated) — if it already holds `suggested_value` the row is treated as already applied (safe re-runs),
5. writes `suggested_value` into that single cell (`suggestion_type: remove` writes `FLAGGED_FOR_REMOVAL` onto the Journal column instead).

Any failed verification leaves the row in the review tab and is reported in the
summary alert — nothing is ever changed based on a stale position alone.

### Archive and deletion semantics

- `approve` and `reject` rows are archived to `<tab>_processed` (created on first use) and deleted from the review tab (in descending row order, in one batch each).
- Approvals whose verification failed stay in the review tab for manual handling.
- `pending` rows are never touched.
- Re-running the script is safe: already-applied rows pass the idempotency check and everything else re-verifies from scratch.

The `Agent_suggestions_processed` archive contains every reviewed AI suggestion;
`Disagreements_processed` archives every reviewed disagreement. Both can be used
to analyze AI-suggestion approval and disagreement quality over time.

## 3. Daily Workflow

1. **Disagreements (deterministic, every pipeline run):** the maintainer runs the *Extract Data* action (`download_sheets.py` → `update_extracted.py` → `data_process.py` → `upload_sheets.py`); step 2 regenerates `logs/disagreements.csv` (all rows `pending`, with precomputed suggested values and target cells) and step 4 uploads it to the `Disagreements` tab. Regeneration resets all statuses to `pending` — review/approve between pipeline runs, otherwise a fresh report replaces the old statuses.
2. **Agent suggestions (non-deterministic, on demand):** run `journal-metadata-enrichment/run_agent.sh`, then `journal-metadata-enrichment/agent/scripts/upload_suggestions.py` to push `Agent_suggestions.csv` to the `Agent_suggestions` tab.
3. Open the spreadsheet and jump to a review tab with **WhereToPublish → Review Disagreements** or **WhereToPublish → Review Agent suggestions**, review the evidence, and set the **Status** dropdown to `approve` or `reject`. A row with an empty `suggested_value` must be filled in (or rejected) first.
4. Click **WhereToPublish → Apply Reviewed Changes**.
5. `approve` rows: the verified cell edit is applied, then the row is archived in `<tab>_processed` and deleted. `reject` rows: archived and deleted without any data change.
6. Sections in the summary alert: applied/rejected/archived counts per tab plus per-row issues for rows left for manual handling.
